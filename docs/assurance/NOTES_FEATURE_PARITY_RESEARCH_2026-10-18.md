# Notes feature parity research — 2026-10-18

> Historical snapshot from before the Markdown implementation. Public persistence fixes and the shared Markdown source editor/preview have since shipped, using the approved multiplatform-markdown-renderer 0.46.0 and code highlighting. See the [current notes contract](../product/MARKDOWN_NOTES.md) for implemented behavior, schema/ABI, limitations, and validation boundaries. Rich attachments, OCR, WYSIWYG editing, retained history, and synchronization remain future work; recommendations and validation results below describe the original research date.

Scope: web research supporting the Chur notes audit, using only manufacturers' documentation and upstream repositories. Sources accessed **18 October 2026**. This records documented capabilities, not hands-on verification of the competing applications or source inspection of Chur. Apple's default guides identified themselves as iOS/iPadOS/macOS 27 when retrieved; Markdown introduction is separately documented for version 26. Unversioned documentation can change.

## Conclusion

“Full Markdown” and “Apple Notes parity” are separate requirements. Apple documents Markdown import **converted into rich text**, and `.md` export; this does not establish source-preserving Markdown editing or lossless round trips. Drawing, scanning, audio, organization, search and collaboration are additional subsystems, not features obtained by adding a Markdown editor. Chur needs explicit contracts for document format, editing, attachments, search, recovery and privacy. [Apple import, available from OS 26](https://support.apple.com/en-us/102223), [Mac export](https://support.apple.com/guide/notes/import-export-and-print-notes-not201900c07/mac), [iPhone export](https://support.apple.com/guide/iphone/export-or-print-notes-iphdf551cfa2/ios).

Here, **ordinary/hidden note** means application visibility; **internet publication** is a separate operation. A `public` code identifier must not itself imply an anonymously accessible web document. Recommendations below are proposed requirements, not claims about existing Chur defects.

## Hidden notes: Apple's restrictions are not Chur's target

Apple locked notes protect contents with end-to-end encryption. Their titles remain visible. Notes containing tags, audio/video/PDF/file attachments, Quick Notes, shared notes and third-party-account notes cannot be locked. Opening one locked note temporarily opens other locked notes in the same account. Resetting a forgotten custom password does not recover previously locked notes. This differs substantially from hiding a note's existence and metadata. [iPhone locking rules](https://support.apple.com/guide/iphone/lock-notes-iphf177bb154/ios), [E2EE and the two locking methods](https://support.apple.com/en-nz/102537), [Apple Platform Security, published 19 December 2024](https://support.apple.com/en-gb/guide/security/sec1782bcab1/web).

**Chur recommendation:** use one document capability model for ordinary and hidden notes. The access mode should control key access, indexes, previews, history, links and export. It should not silently downgrade the editor. OCR/transcripts from hidden attachments must not enter an ordinary search domain. Publishing or sending a copy is a separate explicit action. Historical versions must either remain within the protected domain or be explicitly removed when protection changes; an accessible old copy defeats the new protection. These are design recommendations, not confirmed findings about Chur's current behavior.

Apple documents shared-note activity and change highlights. The reviewed guides do not establish a complete contract for browsing and restoring all historical versions of personal notes. Revision history should therefore be a Chur requirement in its own right rather than an unverified Apple feature claim. [Activity](https://support.apple.com/guide/iphone/share-and-collaborate-iphe4d04f674/27/ios/27).

## Lessons from open-source applications

| Application | Verified approach | Limitation / lesson |
| --- | --- | --- |
| Joplin | Markdown storage with a Rich Text editor; offline PNG/JPEG/PDF OCR; SQLite FTS4; separate synchronized history and optional E2EE. [Editor](https://joplinapp.org/help/apps/rich_text_editor/), [OCR](https://joplinapp.org/help/apps/ocr/), [search](https://joplinapp.org/help/apps/search/), [history](https://joplinapp.org/help/apps/note_history/), [E2EE](https://joplinapp.org/help/apps/sync/e2ee/) | Rich Text can lose HTML/plugin formatting; tables require headers and reference links become inline links. OCR processing runs on desktop, with results available on mobile through sync; handwriting is unsupported. Revisions are recorded every ten minutes, retained for 90 days by default, and viewed on desktop. E2EE requires enabling. Do not promise arbitrary Markdown-to-rich-text round trips without loss. |
| Standard Notes | Separate Note Types for plain text, Markdown, rich text, tasks and spreadsheets; E2EE sync, app lock, individual-note protection and revision history. [Features](https://standardnotes.com/features), [repository](https://github.com/standardnotes/app) | Separate document contracts can be safer than silently changing one string's format. Feature availability depends on plan. A complete open-source app/sync product is not automatically an embeddable Kotlin/Swift/Rust library. |
| Notesnook | Rich editor with Markdown import/export; a private vault over baseline E2EE; shared editor package with a mobile wrapper. [Markdown behavior](https://notesnook.com/help/rich-text-editor/markdown-notes-editing), [vault](https://notesnook.com/help/lock-notes-with-private-vault), [architecture](https://github.com/streetwriters/notesnook) | Its documentation explicitly says Markdown shortcuts are not raw Markdown editing. The vault uses a separate password and deletes previous note versions when locking. This demonstrates the historical-copy protection problem; it does not justify silently losing Chur users' history. |

Notesnook also separates history, backup and publication: history is local and cleared on logout; backups are encrypted by default; Monographs publish a separate copy updated through a distinct action, optionally password-protected. These are different lifecycles that Chur should specify independently. [History](https://notesnook.com/help/note-version-history), [backup](https://notesnook.com/help/backup-and-restore-notes-in-notesnook), [publication](https://notesnook.com/help/publish-notes-with-monographs).

The source code is useful as an architectural reference, but reuse requires package-level license review: Joplin defaults to AGPL-3.0-or-later with directory exceptions; Standard Notes app identifies AGPL-3.0; Notesnook identifies GPL-3.0. These are repository license facts, not a legal conclusion about a particular integration. [Joplin license](https://github.com/laurent22/joplin/blob/dev/LICENSE), [Standard Notes repository](https://github.com/standardnotes/app), [Notesnook repository](https://github.com/streetwriters/notesnook).

## Proposed measurable feature sequence for Chur

1. **Working Markdown:** an explicit dialect, source editing and preview; headings, nested lists, task lists, tables, fenced code, links/images and blockquotes; preserve unsupported source text; `.md` import/export with attachments and an honest account of unrepresentable blocks. Ordinary and hidden notes use the same semantics.
2. **Daily note workflows:** autosave with an observable result, undo/redo, find/replace, folders/tags/pins, trash/restore, links/backlinks, local search and revision restore. History receives the current version's protection.
3. **Materials inside notes:** real image/file/PDF/audio attachments with preview/export; then camera scanning, markup/drawing, OCR and local transcription. Each capability includes failures, cancellation, limits and cleanup.
4. **Sync and collaboration:** offline/conflict/recovery guarantees and attachment transfer, followed by participant roles, invitations, revocation and live editing. Internet publishing is distinct from own-device sync.
5. **Expensive capabilities:** handwriting recognition/refinement, computed math and AI summaries, evaluated separately for Russian-language quality, model size, licensing, Android/iOS availability and privacy.

This is an order of runnable product capabilities, not a promise of a single implementation phase. No parser/editor alone supplies attachment custody, key handling, history, sync or private search. Library selection must follow the document-format and ordinary/hidden access contracts.
