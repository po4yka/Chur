The Android page callback reports the final page count after child recognition returns. Its item-level indeterminate progress is consistent with the current product contract; live per-page Android progress was not added. Clear refuses while a cancelled scan still owns an in-flight write. This is a required drain boundary, not an instruction to erase the index before the writer stops.

## Native persistence and erasure

No new native production defect was confirmed. The audit checked bound SQL parameters, literal FTS prefixes, mixed metadata and content terms, Cyrillic, stable candidate pagination, source identity, active-state and engine checks, strict FFI records, SQLCipher, FTS secure deletion, Trash, restore, purge and full versus selective archives.

New tests use actual native containers and the C ABI. They check local and signed remote purge through restart and full backup/restore, absent content rows and FTS vocabulary, rejected stale writes, and the healthy neighbor's searchable text and exact original bytes. Clearing while an item is in Trash must prevent its old recognized text from returning after restore. Malformed controls must preserve existing index rows, FTS terms and originals. Each writable output count starts from a nonzero sentinel. After every rejected control, a real password unlock compares all content-index rows, the full FTS vocabulary and catalog generation with their prior SQLCipher state. The C session then reopens for the next call. These final test-only refinements passed all 16 FFI tests after the full workspace run.

The initial current-main workspace passed 783 native tests in 57 targets. The expanded workspace passed 786 tests with no failures, ignored tests or filters. Formatting, all-targets Clippy with warnings denied, and 106 vectors plus two fixtures passed. The Swift package passed all 52 tests. Later proof refinements and platform results are recorded in the final validation section.

## Platform and dependency boundary

Android recognizes English and Russian with the pinned Tesseract4Android AAR and bundled models. The artifact and both model hashes were checked against the declared pins and upstream model revision. All eight 64-bit native libraries in the AAR have 16 KiB LOAD alignment; final APK packaging is a separate check.

The [upstream 4.9.0 release](https://github.com/adaptech-cz/Tesseract4Android/releases/tag/4.9.0) contains Tesseract 5.5.1, Leptonica 1.85.0, libjpeg 9f and libpng 1.6.48. The application accepts only its two hash-pinned models, as required by the [Tesseract trusted-model workaround](https://github.com/tesseract-ocr/tesseract/security/advisories/GHSA-q44c-23p6-5mw6). The packaged libpng version has a [published advisory](https://github.com/pnggroup/libpng/security/advisories/GHSA-wjr5-c57x-95m2). The inspected [bitmap JNI path](https://github.com/adaptech-cz/Tesseract4Android/blob/4.9.0/tesseract4android/src/main/cpp/leptonica/readfile.cpp) copies decoded pixels into a PIX; Chur does not pass an encoded file to Leptonica's PNG reader. No reachable path to the reviewed advisories was established. This does not mean that the native dependency has no vulnerabilities. The existing [dependency review](../DEPENDENCY_POLICY.md#tesseract4android-490-and-bundled-englishrussian-models) remains applicable.

The Android decoder is a private process with the application UID. Its separate process and explicit descriptor custody do not establish a separate-UID security sandbox. OCR uses the existing decoder mutex, PID handshake, bounded output, kernel-exit barrier and failed-owner gate. No model download, OCR network call, private plaintext scratch file or system-search publication was found in the inspected path.

Apple documents [`VNRequest.cancel()`](https://developer.apple.com/documentation/vision/vnrequest/cancel()) as an attempt to stop a request as soon as possible. Core Graphics decode and PDF rendering remain synchronous. Cancellation must drain them; this audit does not promise a bounded wall-clock stop or physical memory erasure. Late output must not enter the index or UI.

## Verification boundaries

Physical-device extraction, hardware file protection, power-loss behavior and production acceptance remain separate gates. SQLCipher row removal and owned-buffer cleanup do not erase historical backups, previously exported plaintext, authorized recipient copies or all physical flash and memory remnants. Actual recognition tests do not prove OCR accuracy for every font, image, language or layout.
