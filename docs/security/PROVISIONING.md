# Vault Provisioning and First Run

> **Status:** Proposed normative creation flow

Every other document describes a vault that already exists. This one describes the moment it does not: what the application generates, what it requires before it opens, and what it tells the user before the first private byte is written.

The byte-level transaction is owned by [`../format/VAULT_DESCRIPTOR_V1.md`](../format/VAULT_DESCRIPTOR_V1.md) §9 and is not restated here; this document fixes the product policy around it. The slot rule it depends on is fixed by [ADR-0032](../adr/0032-vault-creation-requires-a-password-slot.md).

## 1. Scope

Covers first launch, public-shell selection, vault creation, and the first teaching of the access route. It does not cover unlock ([`KEY_SLOTS.md`](KEY_SLOTS.md) §8), recovery ([`RECOVERY.md`](RECOVERY.md)), backup restore ([`RECOVERY.md`](RECOVERY.md) §7), or decoy provisioning ([`DECOY_VAULT.md`](DECOY_VAULT.md) §3).

## 2. First launch

First launch opens the public shell. It does not open a vault flow.

- no vault exists and none is created until the user asks for one;
- the public shell is usable immediately, with no account, no permission prompt, and no key generation;
- v1 ships one shell, Notes, and selects it without asking. A release that ships a second shell adds the choice here and in [`../product/DISCREET_MODE.md`](../product/DISCREET_MODE.md);
- the public-shell disclosure required by [`../product/DISCREET_MODE.md`](../product/DISCREET_MODE.md) is shown the first time the user writes public-shell content, not during vault creation;
- the route to vault creation is a visible settings entry. A hidden gesture is configured later, from an unlocked session, and never replaces the visible route.

## 3. Creation

When the user asks to create a vault, the application must, in this order:

1. explain what the vault protects, and that no server copy exists and no support path can recover it;
2. take the password and check it against [`PASSWORD_PROFILE.md`](PASSWORD_PROFILE.md);
3. run the transaction of [`../format/VAULT_DESCRIPTOR_V1.md`](../format/VAULT_DESCRIPTOR_V1.md) §9, which generates the `VaultRootSecret` at its first step;
4. verify the password slot by unwrapping the committed root with the entered password, before the descriptor reaches `ACTIVE`;
5. offer the recovery slot under §4;
6. reach `ACTIVE` and open the session;
7. offer the device slot under §5;
8. teach the access route under §6.

The password slot is mandatory. No path through this flow reaches `ACTIVE` without one, and no import is possible before `ACTIVE`. A crash at any step leaves no openable vault, per §9 of the descriptor specification.

The root secret is generated by Rust from the OS CSPRNG at step 3 and at no earlier point. No password, device identifier, or other user input contributes to it; the password derives a KEK only, as SEC-001 requires.

## 4. Recovery slot

The recovery slot is offered during creation, before the first import.

- the offer states that a forgotten password with no recovery slot is unrecoverable, and that support cannot help ([`RECOVERY.md`](RECOVERY.md) §10);
- the user may decline. Declining is an explicit choice, not the dismissal of a sheet, and is recorded only as non-secret public state;
- a declined offer is repeated once after the first import completes, and the entry stays in settings permanently;
- accepting runs the presentation and confirmation of [`RECOVERY.md`](RECOVERY.md) §2 before the slot commits;
- the recovery representation is never shown again afterwards; a user who loses it rotates the slot under [`RECOVERY.md`](RECOVERY.md) §8.

## 5. Device slot

The device slot is offered after the vault is `ACTIVE`, never before.

- the offer names the policy being chosen under [`KEY_SLOTS.md`](KEY_SLOTS.md) §1: convenient mode makes the device unlock code a working vault credential, strict mode does not. The copy states that consequence rather than recommending a mode;
- declining leaves the password as the only unlock factor, which is a supported configuration;
- the device slot is never the only slot. Removing the last portable slot is refused, because [`KEY_SLOTS.md`](KEY_SLOTS.md) §9 requires a verified recovery path to remain through every slot update.

## 6. Access route

At the end of creation the application shows how to reach the vault again and confirms the user can do it.

- the visible settings entry of §2 always works and cannot be removed in v1;
- an optional hidden gesture or route is configured later, from an unlocked session, under the constraints of [`../product/DISCREET_MODE.md`](../product/DISCREET_MODE.md);
- the accessible alternative that document requires is offered in the same step, not buried as a separate setting.

## 7. Decoy

A decoy vault is never provisioned at first run. It is created from an authenticated real session under [`DECOY_VAULT.md`](DECOY_VAULT.md) §3, and its creation runs §3 to §6 of this document for the decoy identity. Creation copy for the real vault does not mention the decoy feature; the feature is found in settings.

## 8. Creation must not

- generate a root secret before the user asks for a vault;
- create a vault with no portable slot;
- import media before the descriptor is `ACTIVE`;
- write anything into public storage beyond the non-secret fact that onboarding completed;
- state a claim that [`../product/DISCREET_MODE.md`](../product/DISCREET_MODE.md) forbids;
- request a permission the flow does not use.

## 9. Required tests

- creation interrupted at each step of [`../format/VAULT_DESCRIPTOR_V1.md`](../format/VAULT_DESCRIPTOR_V1.md) §9, then restarted: no openable vault, no orphaned directory, no residual root material;
- the flow cannot reach `ACTIVE` without a verified password slot;
- declining recovery re-offers the slot after the first import;
- declining the device slot leaves an unlockable vault;
- public storage after creation holds no vault identifier, slot data, or object count;
- decoy creation runs the same flow and leaves no cross-identity state ([`DECOY_VAULT.md`](DECOY_VAULT.md) §11).
