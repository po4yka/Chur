# Chur Recovery

> **Status:** Proposed normative recovery model

Recovery restores access to the random `VaultRootSecret`; it does not reset encryption through a server-held master key. If every valid factor and every recoverable backup is lost, data loss is intentional and irreversible.

## 1. Supported modes

### Device-bound

Only a platform slot exists. Highest local binding, no portable recovery. Device loss, uninstall, or slot invalidation may permanently destroy access.

### Recoverable local vault — recommended default

```text
device slot       → daily unlock
password slot     → portable fallback
recovery slot     → high-entropy emergency fallback
```

The user may choose password only or recovery only if product policy permits, but the risk must be explicit.

### Multi-device/synced

Adds authenticated peer-device enrollment and remote ciphertext. This requires device identity, operation-log, rollback, and revocation specifications.

## 2. Recovery secret

`RecoverySecret` is 32 random bytes generated by Rust CSPRNG. It is encoded for humans as a versioned mnemonic, QR, or both.

Presentation requirements:

- checksum and profile/version;
- canonical binary round trip;
- clear word separation and typography;
- offline display/print option;
- explicit warning not to store beside an unlocked device;
- confirmation by re-entry or verified scan;
- no upload to Chur server in plaintext.

## 3. Recovery slot

```text
RecoveryKEK = HKDF-SHA-256(RecoverySecret, recovery context)
wrapped_root = approved AEAD.seal(
    key = RecoveryKEK,
    nonce = fresh random,
    plaintext = VaultRootSecret,
    aad = canonical RecoverySlot context
)
```

The stored slot contains no plaintext recovery secret.

## 4. Recovery matrix

| Event | Device slot | Password | Recovery | Result |
| --- | ---: | ---: | ---: | --- |
| biometric set changed | invalid | valid | optional | unlock with password/recovery; re-enroll device |
| device lost, portable backup exists | lost | valid | optional | restore and create new device slot |
| password forgotten | valid | unavailable | valid | unlock with recovery; replace password slot |
| application deleted, no backup | lost | valid | valid | credentials alone cannot recreate missing ciphertext |
| backup exists, every credential lost | lost | lost | lost | irrecoverable |
| one catalog/object corrupt | valid | valid | valid | recovery of keys does not repair missing ciphertext; restore/repair needed |
| recipient revoked | n/a | n/a | n/a | recovery does not revoke copies already obtained |

## 5. Password recovery flow

1. authenticate the recovery secret locally;
2. unwrap and validate the root/vault context;
3. open a restricted recovery session;
4. create a new password slot with fresh salt/parameters;
5. verify and commit it atomically;
6. optionally re-enroll platform slot;
7. preserve or rotate recovery according to user choice;
8. close restricted session.

The server, email, and support staff do not receive the root or recovery secret.

## 6. Device-slot recovery

When Keystore/Keychain slot is invalidated:

- surface `PLATFORM_KEY_INVALIDATED` without implying data loss;
- request password or recovery;
- validate the vault first;
- create and verify a replacement platform slot;
- retire stale alias/item references;
- retain portable slot throughout the transaction.

## 7. Backup restore

Restore is transactional:

1. parse and bound backup manifest;
2. identify supported portable slots;
3. authenticate one slot and manifest context;
4. verify inventory and object completeness;
5. restore into a temporary opaque vault directory;
6. rebuild/verify catalog as specified;
7. commit vault descriptor atomically;
8. create a new device slot;
9. never import device-bound aliases from another device.

## 8. Rotation

Recovery rotation:

- generate a new secret;
- create/verify new slot;
- require user confirmation that the new representation was stored;
- commit new descriptor generation;
- remove old slot only after success;
- explain that old backups containing the old slot may remain recoverable with the old secret.

Revoking old recovery across backups requires re-encrypting/re-exporting backup manifests or accepting that old backups remain valid.

## 9. Real and decoy recovery

Each identity has independent recovery. UX must not reveal sibling identities. A recovery package for one vault must not enumerate another.

## 10. Support boundaries

Support can help diagnose format/version/platform errors using redacted information. Support must never request:

- password;
- recovery words/QR;
- root, collection, or object keys;
- real private media;
- an unredacted production vault.

Synthetic reproduction and structural ciphertext diagnostics are preferred.

## 11. Required tests

- every factor combination in the matrix;
- one-bit recovery-secret error and checksum failure;
- wrong vault binding;
- slot replacement crash at each step;
- old/new backup interaction after rotation;
- restore across Android, iOS, and CLI;
- missing/corrupt object despite valid keys;
- device invalidation and re-enrollment;
- real/decoy isolation;
- no plaintext secret in logs, screenshots, clipboard, or saved state.
