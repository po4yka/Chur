# ADR-0032: Vault Creation Requires a Verified Password Slot

- **Status:** Accepted
- **Date:** 2026-08-27
- **Decision owners:** @po4yka
- **Related:** [`../security/PROVISIONING.md`](../security/PROVISIONING.md), [`../security/RECOVERY.md`](../security/RECOVERY.md), [`../security/KEY_SLOTS.md`](../security/KEY_SLOTS.md), [`../format/VAULT_DESCRIPTOR_V1.md`](../format/VAULT_DESCRIPTOR_V1.md)

## Context

`VAULT_DESCRIPTOR_V1.md` §9 fixes the initialization transaction down to its commit order, `RECOVERY.md` §1 calls the recoverable configuration a recommended default without naming who enforces it, and `KEY_SLOTS.md` §1 says a recoverable vault should have a portable slot. Nothing decided what the creation flow actually requires. The device-bound mode whose loss `RECOVERY.md` §1 calls permanent was therefore reachable by a user who skipped a step, and every other document specified unlock, lock, recovery, rotation, restore, migration, or revocation for a vault whose creation was unspecified.

## Decision

- The `VaultRootSecret` is generated by Rust from the OS CSPRNG at step 1 of the §9 transaction and at no earlier point. No user input contributes to it.
- Creating a vault requires exactly one mandatory slot: a password slot, created and verified before the descriptor reaches `ACTIVE`. It is not skippable and it cannot be the last portable slot removed.
- The recovery slot is offered during creation and may be declined once, with the consequence stated. It is re-offered after the first import completes and stays available in settings.
- The device slot is offered only after the vault is `ACTIVE`, and is never the only slot.
- The product therefore creates no device-bound-only vault in v1. The format still accepts one and `VAULT_DESCRIPTOR_V1.md` §14 still tests one, because a future peer-device or managed profile may reintroduce it under its own ADR.

## Alternatives considered

### Make the recovery slot mandatory as well

Rejected. A recovery phrase forced on a user during creation gets photographed or written on the device, which turns a recovery factor into a disclosure. A password the user chose is portable without leaving an artifact, and the recovery slot is offered again once the vault holds something worth recovering.

### Let the device slot alone create a vault

Rejected. That is the irreversible-loss mode reached by the shortest path in the flow, and platform key invalidation is an ordinary event rather than a rare one.

## Consequences

### Positive

- every vault the product creates has a portable factor, so the `RECOVERY.md` §4 matrix always has a valid row;
- the recommended default of `RECOVERY.md` §1 gains an enforcing document;
- the first-run flow can be tested against a fixed order and a fixed refusal.

### Tradeoffs

- a user who wants biometric-only convenience still types a password once;
- password quality becomes the floor for every vault, which `PASSWORD_PROFILE.md` must carry.

## Security impact

Affected invariants: SEC-002, SEC-006, SEC-009, SEC-055.

The decision removes a reachable state in which one platform-key invalidation destroys the vault, and it fixes the moment at which the root secret first exists, which SEC-002 asserts but no flow document previously located.

## Compatibility impact

No persisted or wire bytes change. A descriptor carrying no password slot stays readable; the product does not create one.

## Validation

- creation interrupted at each step of `VAULT_DESCRIPTOR_V1.md` §9 leaves no openable vault;
- the flow cannot reach `ACTIVE` without a verified password slot;
- removing the last portable slot is refused;
- a declined recovery offer is repeated after the first import.

## Follow-up

- `PASSWORD_PROFILE.md` states the minimum accepted at creation;
- the creation rows are added to the `RECOVERY.md` §11 test list.
