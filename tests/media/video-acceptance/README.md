# Video acceptance fixtures

This matrix adds real encoded stress clips and a small upstream Dolby Vision
camera-origin clip. It complements `../hevc-main10`; those six color-signal
fixtures remain unchanged. All three generated MP4 files have HEVC Main 10,
10-bit 4:2:0, BT.709 SDR, `hvc1` and AAC audio.

| File | Input and purpose | Suggested seeks |
| --- | --- | --- |
| `main10-4k60.mp4` | 3840 × 2160, 60 fps, 150 frames, 2.5 seconds. Exercises full-resolution decode, frame rate and bounded poster work. | 0.5, 1.5 seconds |
| `main10-long-gop-vfr.mp4` | 320 × 180, 64 seconds. Presentation intervals alternate between 20, 40 and 80 ms. Key frames occur approximately every 16 seconds. Exercises nonuniform timestamps, sparse sync frames and seeks far from the start. | 0.5, 31, 55, 62 seconds |
| `main10-portrait-rotation.mp4` | Coded 1920 × 1080, 24 fps, 2.5 seconds, with a 90-degree display matrix. Display dimensions are 1080 × 1920. Exercises upright bounds and posters. | 0.5, 1.5 seconds |
| `camera-dolby-vision.mov` | Unchanged AndroidX Media test asset. HEVC Main 10, Dolby Vision profile 8, HLG base layer, RPU metadata, coded 1280 × 720, -90-degree display matrix. Display dimensions are 720 × 1280. | None: the clip lasts only about 0.107 seconds. |

The generated clips contain moving `testsrc2` color texture and a 440 Hz tone.
They are not black placeholders. The VFR source starts at 50 fps and selects
frame indices 0, 1 and 3 in each seven-frame group. It retains source timestamps.
The generator probes decoded presentation times and key frames; the manifest
records the observed intervals, frame counts and sync-frame times. The small
long-GOP clip tests seek mechanics, not high-bitrate or large-file throughput.
The short 4K clip tests this encoded input, not all 4K60 cameras or sustained
thermal behavior.

## Dolby Vision source and license

`camera-dolby-vision.mov` is a byte-identical copy of
[`dolbyVision-hdr.MOV` in AndroidX Media](https://github.com/androidx/media/blob/dac651634e15a8a97076037fd81285de18d86d62/libraries/test_data/src/test/assets/media/mp4/dolbyVision-hdr.MOV).
It was added by the upstream change
[`2db2de59933f87e7b76cbaefda56d25633bf252d`](https://github.com/androidx/media/commit/2db2de59933f87e7b76cbaefda56d25633bf252d).
The pinned repository revision is
`dac651634e15a8a97076037fd81285de18d86d62`. The repository distributes it under
the [Apache 2.0 license](https://github.com/androidx/media/blob/dac651634e15a8a97076037fd81285de18d86d62/LICENSE).
`LICENSE.androidx-media` contains that license. `NOTICE` records attribution
and the local filename change. No upstream root `NOTICE` exists at that revision.

Embedded capture metadata identifies Apple, iPhone 14 Pro and iOS 16.4.1.
Camera origin is therefore **inferred from the source asset and its capture
metadata**. It is not independently witnessed or verified from a recording log.
The manifest uses `genuine_camera: null` and states this limit rather than
asserting an observed camera session. The original public upstream metadata
remains in the unchanged file. The manifest lists only device identification
metadata and does not repeat capture coordinates.

This file contains a real Dolby Vision configuration record (profile 8, base
layer compatibility ID 4) and per-frame Dolby Vision RPU data. It is not a
synthetic video with a Dolby Vision tag. It has five compressed video samples;
FFmpeg exposes four presentation frames inside its short edit interval. Test
initial frame/poster decode, metadata, native output selection and exact original
export. Do not require playback past 0.12 seconds or use this asset for a long
seek test. Software decode verifies the HEVC/HLG base layer and presence of RPU
data; it does not establish Dolby Vision rendering or display output.

## Regeneration and validation

From the repository root:

```sh
python3 tests/media/video-acceptance/generate.py
```

The script requires Python 3, FFmpeg with libx265/AAC, and ffprobe. It uses one
encoding thread, fixed patterns, fixed timestamps and bounded commands. It
generates into a temporary directory, validates each output, then replaces only
the listed fixture files and manifest. It downloads the pinned camera file and
license only when local copies are absent. Camera acquisition is limited to
100000 bytes and must match its pinned length and SHA-256 hash. The complete
video matrix must fit within 20 MB. The script never captures a user's camera
or accesses Photos.

Each file has `filename`, `length`, `sha256`, `role`, `genuine_camera`, `ffprobe`
and `timing` fields in `manifest.json`. Generation checks codec/profile, pixel
format, actual dimensions, 4K60 frame count, VFR timestamp diversity, long-GOP
spacing, rotation, Dolby Vision configuration/RPU presence, and complete
software decode. Encoder versions can change generated bytes. Treat checked-in
files and hashes as the acceptance inputs. The original camera bytes are pinned
independently of the installed encoder.

Android exposes these through the existing `tests/media` instrumentation asset
source. iOS tests read the same repository fixture directory. A host, simulator
or software-decoder result does not establish physical-device HDR output,
hardware decoder support, energy use or visual camera acceptance.
